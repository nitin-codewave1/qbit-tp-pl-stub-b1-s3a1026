# TC-005-07: Concurrent PATCH yields standard last-write/conflict

**Story:** [[US-005-03]]
**Module:** ensure no real-time collaboration channel (WebSocket/SSE) exists on notes_api
**Kind:** api

## Preconditions
Existing note, two concurrent PATCH clients

## Expected Result
the API applies a standard last-write/conflict response with no live broadcast or merge logic

## Acceptance Criteria
- notes_api:AC-005-03-02: Given two clients submit PATCH requests to the same note concurrently, when both requests are processed, then the API applies a standard last-write/conflict response with no live broadcast or merge logic

## Planned API Steps

| # | Instruction | Action | Target | Value |
|---|---|---|---|---|
| 1 | Create note | request | `POST /notes` | {"title":"T","body":"B"} |
| 2 | Store id | store | `$.id` | noteId |
| 3 | Send two concurrent PATCHes with different titles | request | `PATCH /notes/{{noteId}}` | {"title":"A"} and {"title":"B"} concurrently |
| 4 | Each response is 200 or 409 | assert_status | `response` | 200|409 |
| 5 | Read final note | request | `GET /notes/{{noteId}}` |  |
| 6 | Final title is one of the written values (no merge) | assert_json | `$.title` | A|B |
