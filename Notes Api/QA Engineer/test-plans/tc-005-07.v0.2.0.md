# TC-005-07: Concurrent PATCH is last-write with no merge

**Story:** [[US-005-03]]
**Module:** ensure no real-time collaboration channel (WebSocket/SSE) exists on notes_api
**Kind:** api

## Preconditions
two clients submit PATCH requests to the same note concurrently

## Expected Result
the API applies a standard last-write/conflict response with no live broadcast or merge logic

## Acceptance Criteria
- notes_api:AC-005-03-02: Given two clients submit PATCH requests to the same note concurrently, when both requests are processed, then the API applies a standard last-write/conflict response with no live broadcast or merge logic

## Planned API Steps

| # | Instruction | Action | Target | Value |
|---|---|---|---|---|
| 1 | Create note | request | `POST /notes` | {"title":"Base","body":"B"} |
| 2 | Store id | store | `$.id` | noteId |
| 3 | Client A patches title | request | `PATCH /notes/{{noteId}}` | {"title":"From A"} |
| 4 | A succeeds | assert_status | `status` | 200 |
| 5 | Client B patches title | request | `PATCH /notes/{{noteId}}` | {"title":"From B"} |
| 6 | B gets 200 (last write); a 409 would also be a standard conflict | assert_status | `status` | 200 |
| 7 | Fetch note | request | `GET /notes/{{noteId}}` |  |
| 8 | Last write wins, no merged value | assert_json | `$.title` | From B |
